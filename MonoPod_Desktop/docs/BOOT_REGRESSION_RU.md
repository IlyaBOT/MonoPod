# Регресс запуска MonoPod v0.9.0 — разбор и исправление

В присланном логе найдено реальное переполнение стека сканера SD. Это произошло до создания framebuffer и до инициализации TFT. Исправление включено в отдельную ветку v0.10.0, обе конфигурации пересобраны. Запуск исправления на физической плате остаётся UNVERIFIED.

## Доказательства из точной сборки

В логе указан `ELF file SHA256: 3f759dc29`. Найден ELF из Arduino-кэша со SHA-256 `3f759dc291828a9e...`; полный хеш и FQBN сохранены в [matching-elf.json](boot-regression/matching-elf.json). Использован именно этот ELF, не символы от другой версии.

Декодированный стек: `setup → MediaLibrary::begin → rescan → scanFolder → scanFolder → SD.open/fopen → heap/free/lock → interrupt watchdog`. Полный [decoded-backtrace.txt](boot-regression/decoded-backtrace.txt) прилагается. `display.begin()` следует после `media.begin()` и до него выполнение в этом сбое не дошло.

В точном ELF `MediaLibrary::scanFolder` начинается с `entry a1, 0x1140`: 4416 байт на вызов. В crash log адреса SP двух соседних уровней `0x3fce9ce0 → 0x3fceae20 → 0x3fcebf60` отличаются на те же 4416 байт. Функция `getArduinoLoopTaskStackSize()` возвращает 8192. Два кадра сканера занимают 8832 байта, ещё без setup и файловой системы. Переполнение следует непосредственно из машинного кода и наблюдаемого стека. См. [old-stack-disassembly.txt](boot-regression/old-stack-disassembly.txt).

В v0.9.0 появился `probeMp3Duration` с локальным `uint8_t b[4096]`. Компилятор -Os встроил его в рекурсивный scanFolder, поэтому окно зарезервировано в каждом уровне, даже когда текущая запись — каталог. В локальном ELF v0.8.9.2 кадр сканера составляет 304 байта.

Сообщение `esp_task_wdt_reset: task not found` само по себе говорит о попытке feed незарегистрированной задачи; оно не доказывает, что нужно отключить watchdog. Причина конечной паники в логе — Interrupt WDT во время ожидания heap lock. Точный вызывающий участок всех ранних task_wdt-сообщений по одному этому логу не установлен. Watchdog не отключался и его таймаут не увеличивался. Различие TWDT/IWDT описано в [официальной документации Espressif](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/wdts.html).

## Исправление и проверки

4096-байтовое окно MP3 теперь выделяется на heap через `new(std::nothrow)` и освобождается RAII после чтения. Отказ выделения оставляет длительность неизвестной и не срывает загрузку. Буфер не живёт в стеке рекурсивного обхода. Ограничение глубины 6 сохранено. Такое же исправление внесено в Wokwi-вариант. Framebuffer 160×128 RGB565, GPIO15, аудиодрайвер и штатный интерфейс не откатывались.

| Реальный ELF | Кадр scanFolder |
|---|---:|
| Локальная v0.8.9.2 | 304 байта |
| v0.9.0 из crash log | 4416 байт |
| Исправленная v0.10.0, S3 | 352 байта |
| Исправленная v0.10.0, ESP32 | 352 байта |

`tools/verify_firmware_stack.py` проверяет prologue обоих итоговых ELF: кадр не больше 512 байт, восемь активных кадров с учётом входа в depth guard занимают не больше 4096 байт. Фактически это 2816 байт; драйверам и остальному стеку остаётся пространство. Это статический предел сканера, а не измерение общего runtime high-water. [stack-verification.json](boot-regression/stack-verification.json) содержит хеши ELF и результаты.

`tools/run_library_tests.py` компилирует настоящий Library.cpp через MSVC с изолированным файловым адаптером. Проверены семь уровней сканирования 0…6, запрет depth 7, MP3 Xing, WAV, неизвестная длительность пустого файла, повторный rescan и eject. Результат — [library-native-tests.json](library-native-tests.json). 70 Python-тестов прошли, три GCC-проверки пропущены. Обе Arduino-компиляции успешны; S3: 1 454 610 байт приложения, 63 020 статической RAM; ESP32: 1 455 019 и 58 428 байт соответственно.

Изменены только новые исходники v0.10.0. Историческая v0.9.0 не перезаписана; отдельный [patch Library.cpp для v0.9.0](boot-regression/fix-v0.9.0-Library.patch) прилагается. Готовые проверенные компиляцией бинарники относятся к v0.10.0.

## Время сборки

Повторная сборка Arduino-ESP32 3.3.12 с сохранёнными объектами: S3 — 189.24 s, 8 jobs; ESP32 — 133.10 s, 4 jobs. Замеры в `build-s3-timing.json` и `build-esp32-timing.json`. Во время сборки наблюдались повторные проходы препроцессора Arduino для поиска библиотек, в том числе большого ESP8266Audio/SD/GFX дерева. Само исправление добавляет лишь стандартные memory/new и не требует новых библиотек.

В `tools/build_firmware.ps1` используются раздельные постоянные `work/build-s3` и `work/build-esp32`, без `--clean`. Первый запуск после переноса проекта будет дольше, поскольку архив не содержит локальный build-кэш. Пример из корня Desktop:

```powershell
.\tools\build_firmware.ps1 -Board s3 -Jobs 4
.\tools\build_firmware.ps1 -Board esp32 -Jobs 4
```

Не запускать две сборки одного профиля в один build-каталог. Скрипт только компилирует и не обращается к COM, не прошивает плату, не форматирует SD.

## Что проверить на плате

Использовать соответствующий S3 N16R8 профиль. После ручного обновления проверить UART0: новые строки `Boot: SD mount and library scan`, `Boot: index complete; loop stack low-water=... B`, `Boot: TFT`, `Boot: audio`, `Boot: Wi-Fi and UI` и `Ready`. Затем вложенные папки с той же картой, повторную индексацию, дисплей, воспроизведение и оба Sync. Если новая паника останется, сохранить полный boot log и сверить его ELF SHA с прилагаемым manifest. Реальный запуск, свободный стек и электрическое поведение данным программным тестом не подтверждены.
