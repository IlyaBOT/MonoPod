# Desktop 1.1.1: USB timeout при отправке badapple.bav

## Наблюдение на реальном плеере

Пользователь отправлял файл с ПК через Upload Files. Журнал Desktop 1.1:

```text
23:08:13 Connected: USB | COM18 firmware 0.10.6 protocol 4
23:08:54 Uploading files: MonoPod USB response timed out.
23:09:01 Connecting: TIMEOUT_OR_DISCONNECT
23:09:40 Connected: USB | COM18 firmware 0.10.6 protocol 4
```

Чтение каталога и INFO работало. Идентификатор COM18 — USB VID_303A/PID_1001, аппаратный USB Serial/JTAG ESP32-S3.

## Причина по коду

В установленном Arduino-ESP32 3.3.12 `HWCDC.cpp` создаёт RX-очередь на 256 байт. ISR уже забирает USB-пакет из FIFO и прекращает добавление в очередь при переполнении, теряя остаток пакета. Плеер 0.10.6 не увеличивает эту очередь, но `UsbSync.cpp` запрашивает `NEXT 1024`. Прежний Desktop передавал все 1024 байта одним вызовом SerialPort.Write. Буфер Windows в 16384 байта не увеличивает буфер ESP32.

Это подтверждённое несоответствие размеров в коде и правдоподобная причина наблюдавшегося таймаута приёма. Точный момент потери байтов на исходной попытке не записывался USB-анализатором. Модель очереди с паузой обработки 24 мс воспроизводит потерю 768 из 1024 байт при прежней отправке.

Плеер оставался в Sync, потому что Desktop закрывал неисправный поток и терял соединение, не заканчивая сессию. Посылать `SYNC END` сразу в тот же поток нельзя: до таймаута плеер принимает эти символы как бинарное содержимое файла.

## Исправления

- Логический блок `NEXT 1024` сохранён, но физическая запись разбита на порции до 64 байт с паузой 8 мс между ними. Этот режим совместимости не требует перепрошивки; скорость USB ниже. Пауза Windows может оказаться больше заданной. Для высокой скорости следует исправлять размер RX-очереди и обработку потока в прошивке; Wi-Fi этим ограничением USB не затронут.
- При ожидании блока учитывается 15-секундный таймаут приёмника: до 20 секунд для NEXT, до 60 секунд для финального подтверждения SD. Таймаут сообщает этап и количество отправленных байтов.
- Перед HELLO очищается старый ввод; запоздалый `TIMEOUT_OR_DISCONNECT` от предыдущей передачи не принимается за ответ нового соединения.
- После прерывания Desktop ждёт безопасный интервал с момента последней записи, открывает новое соединение, проверяет HELLO/INFO и отправляет END. В старый бинарный поток команды не добавляются. Восстановление не повторяет загрузку и не перезаписывает целевой файл. При невозможности подтвердить END приложение сообщает об этом явно.
- Номер исправления: 1.1.1 / 1.1.1.0. Обычная синхронизация остаётся активной после успешной передачи до явного End Sync; при аварии выполняется восстановление и завершение.

## Проверки

**116/116** тестов Desktop прошли, включая ограниченную RX-очередь, точность байтов и границ пакетов, безопасную выдержку перед новым соединением, отказ выполнять END на неожиданном устройстве, обработку старого abort-ответа и полный путь восстановления через WinForms. Сборка и self-contained publish успешны; новая программа запускается с изолированными настройками.

Результат дополнительного физического теста, если он разрешён пользователем, сохраняется в `docs/validation-1.1.1/physical-result.json`. Отсутствие этого файла означает, что такой результат не заявляется. Пробник использует только новый `/Desktop_USB_test_20261031.bin` на 32768 байт с `replace=false`, проверяет обратное чтение и удаляет только свой файл. Существующий `/MonoPod/badapple.bav` не загружается повторно и не удаляется.

С разрешения пользователя контрольный тест на **COM18 / firmware 0.10.6** выполнен успешно: **32768 байт**, CRC32 **EE1EBC69**, обратное чтение совпало по SHA-256, пробник удалён, финальный `sync_mode` — **none**. Общая длительность теста — 10,52 с (включая чтение, проверку и End Sync). Размер и время изменения существующего badapple.bav до и после совпали. В тесте использовалась та же сборка MonoPod.Core, что и в опубликованном Desktop. Полный файл badapple.bav повторно не отправлялся; аварийное восстановление проверено программными тестами, без намеренного обрыва реального плеера.

Прошивка и установленный Arduino core не изменялись; автоматического прошивания нет. Старая работающая копия Desktop 1.1 не заменяется во время её выполнения. Используйте новый `publish/win-x64-1.1.1/MonoPod.Desktop.exe`.
