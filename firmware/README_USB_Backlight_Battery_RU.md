# MonoPod v0.10.4 — USB-аудит, фиксированная подсветка, подготовка к калибровке ADC

**Основой послужил полный архив `MonoPod_Firmware_v0.10.4_BAV2_Clock_Cleanup.zip`.** Это патч исходников, а не аппаратно проверенный релиз. MPOD1 v4 и Wi-Fi API не менялись.

## Что исправлено

`Config.h`:

```cpp
constexpr bool TFT_BL_BRIGHTNESS_CONTROL = false;
constexpr bool TFT_BL_ACTIVE_LOW = false;
constexpr float BATTERY_ADC_RATIO = 2.0f;
constexpr float BATTERY_ADC_OFFSET_V = 0.0f;
```

Когда `TFT_BL_BRIGHTNESS_CONTROL=false`, яркость всегда равна 100% при работе: в конце плавного включения LEDC **отключается**, GPIO15 переключается на цифровой HIGH (или LOW при инверсной схеме). При выключении аналогично — постоянный LOW (или HIGH). PWM используется *только* во время 250-мс включения и 400-мс выключения. Меню `Brightness` показывает `Brightness: Fixed 100%`; изменение уровня не выполняется.

Если требуется прежняя регулировка яркости, установить `TFT_BL_BRIGHTNESS_CONTROL=true` и пересобрать. Остальные настройки MonoPod сохранены. ADC по-прежнему опрашивается раз в минуту; его текущая кривая процентов не изменена.

**ВАЖНО:** Если на GPIO15 при логической единице фактически 2,8 В вместо 3,2–3,3 В, вероятно, выход перегружен прямым током подсветки. `digitalWrite(HIGH)` не устраняет падение напряжения на выходном транзисторе GPIO и не делает такую нагрузку безопасной. Следует питать LED/BL через транзисторный ключ с соответствующим ограничением тока. При просадке питания ESP32 возможны сбои, зависания и повреждение GPIO.

## USB и MonoPod Desktop

Проверенные по исходникам свойства USB:

- `Serial` на ESP32-S3 с включённым **USB CDC On Boot** — **native USB** по GPIO19/20, физически USB Full Speed 12 Мбит/с. `Serial0` (GPIO43/44) предназначен для диагностического UART.
- `Serial.begin(115200)` задаёт *line coding* CDC и не ограничивает скорость USB до 115200 бод. Скорость зависит от USB, буферов, stop-and-wait протокола, SD и хоста.
- MPOD1 v4: `MPOD1 HELLO` -> `MPOD1 READY 4 SD=1`; `MPOD1 X INFO` -> `MPOD1 OK {...}`; `MPOD1 SYNC START` -> `MPOD1 OK SYNC_STARTED`; `MPOD1 X PUT <HEX_UTF8_PATH> <SIZE> <CRC32_HEX> <REPLACE>` -> `MPOD1 NEXT N`; затем ровно `N` бинарных байт (без строк/разделителей), повторять NEXT; результат `MPOD1 OK SAVED`; завершение `MPOD1 SCAN`, `MPOD1 SYNC END`.
- **На Windows обязательно проверить C# `SerialPort.DtrEnable=true`.** В .NET оно по умолчанию `false`; в прошивке при передаче выполняется `if(!Serial)` с ошибкой `TIMEOUT_OR_DISCONNECT`. Это **вероятная**, но ещё не подтверждённая по логу причина отказа Desktop. `RtsEnable=false`, `Handshake=None`. Файл `tools/MonoPodDesktop_UsbCdc_Settings.cs.txt` содержит параметры и схему обмена; это не патч отсутствующего проекта MonoPod Desktop.
- Не путать COM-порт чипа USB-UART (CH340/CP210x) с native USB CDC ESP32-S3.
- Протокол подтверждает каждый 1024-байтный блок. SPI microSD настроен на 4 МГц (сырой физический максимум около 0,5 МБ/с без служебных накладных расходов), поэтому реальная передача не достигает 12 Мбит/с. Для оптимизации потребуется увеличить проверенную скорость SPI и реализовать окно/батчи USB-блоков в новой версии протокола *с совместимым изменением клиента*.
- `SYNC END` выполняет пересканирование SD **до ответа**, поэтому на больших медиатеках использовать увеличенный таймаут клиента (например, 30 секунд). Нельзя смешивать текстовые команды с бинарными блоками.

### Порядок тестирования USB на Mac/Windows

Установить pyserial:

```bash
python3 -m pip install pyserial
python3 tools/usb_probe_v4.py                 # список портов
python3 tools/usb_probe_v4.py --port /dev/cu.usbmodem101
python3 tools/usb_probe_v4.py --port /dev/cu.usbmodem101 --cycle
```

На Windows вместо `/dev/cu.usbmodem101` указать `COM11` или свой реальный порт native USB. Без `--cycle` утилита не запускает синхронизацию и ничего не пишет на SD. С `--cycle` выполняет только START/END без передачи файлов, но END вызывает сканирование медиатеки. Для повторного запуска корректно закрывать MonoPod Desktop — COM-порт может быть занят только одним приложением.

Если probe проходит, а MonoPod Desktop нет, проблема находится в настройке его COM-порта, чтении ответа, таймаутах или протокольном парсинге; потребуется конкретный лог и исходники Desktop. Локальный путь `I:\DIY_iPod_Mono` недоступен из этой среды; исходников актуального Windows Forms приложения не было в полученных архивах.

## Аккумулятор

Текущая схема: GPIO4, делитель 100 кОм/100 кОм, идеальный коэффициент 2, измерения `analogReadMilliVolts()` с усреднением 12 отсчётов. Расчёт порогов и процентов **не менялся**. Добавлены только коэффициенты `BATTERY_ADC_RATIO` и `BATTERY_ADC_OFFSET_V` для дальнейшей калибровки.

По текущему коду при реальных 4,06 В на аккумуляторе напряжение GPIO4 около 2,03 В (пользователь измерил 2,01 В — близко). Вычисление даёт ~4,02 В => ~80%, а `Display::batteryBand()` показывает полный значок при >=75%. Следовательно, отображение полного значка не означает реальных 100%.

Падение на регуляторе: 4,22 -> 3,22 В; 4,13 -> 3,13 В; 4,06 -> 3,11 В. Разница около 0,95–1,0 В указывает на большой dropout либо неверную/перегруженную обвязку. При 3,7 В на аккумуляторе напряжение 3,3-В шины может оказаться около 2,7–2,8 В, что уже ниже штатного питания ESP32-S3. Нельзя компенсировать такое поведение только перестановкой нижнего порога SoC: питание может стать нестабильным значительно раньше разряда Li-ion до безопасного предела.

**Для следующего этапа**: при стабильном полном заряде, снятом зарядном токе, измерить Vbat, V(GPIO4), программный `BATTERY=` по UART, а также V(3V3) под обычной нагрузкой и во время Wi-Fi/аудио. Не оставлять Li-ion выше допустимого напряжения заряда; 4,22 В требует проверки точности вольтметра и контроллера заряда.
